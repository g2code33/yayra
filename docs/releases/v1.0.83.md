# Yayra v1.0.83 — Google account reflection and Gmail return-to-app

Yayra 1.0.83 repairs the Google continuation loop that previously verified an
account in Chrome but then abandoned the initiating Yayra tab, reopened only a
product origin externally, or returned to a Google page that still looked
unconnected.

## What changed

### Exact initiating-tab continuation

- First-party Google account interception now retains the complete validated
  Google-product destination: path, query, and fragment, not only its origin.
- After the verified OAuth callback, Yayra resumes that destination
  automatically in the same tab and window that initiated sign-in.
- The selected Google profile is applied from both the live auth event and the
  authenticated invoke result, so a hidden/reloaded renderer cannot miss the
  one-shot completion.
- Connected Google pages receive a persistent Yayra account strip showing the
  exact selected email/avatar. The strip remains separate from Google's own
  cookie-dependent website controls and links directly to Gmail inside Yayra.
- Web/PWA restoration re-establishes the in-app-only Google route instead of
  auto-opening a restored Google destination in another browser.

### Gmail opens inside Yayra

A Gmail-initiated sign-in now requests the explicit
`https://www.googleapis.com/auth/gmail.readonly` scope during the same external
OAuth trip. On return, the exact Gmail tab opens an in-Yayra mailbox surface for
the selected account.

The first production surface supports:

- inbox, unread, starred, sent, and all-mail views;
- Gmail search queries;
- paginated message summaries;
- opening bounded plain-text message bodies; and
- a persistent account header naming the exact verified email.

It is intentionally read-only. It does not compose, send, delete, archive,
modify labels, load remote email HTML, or fetch attachments.

### Token isolation on every platform

- **Electron desktop:** Gmail OAuth credentials remain in the profile-scoped,
  OS-keychain-encrypted main-process auth store. List/message calls run behind
  IPC; renderer JavaScript receives only normalized message data.
- **Web/PWA:** the callback stores only a random 43-character `YayraGmail`
  capability. Raw Google credentials remain AES-GCM-encrypted in Cloudflare KV.
- **Android/iOS:** the Custom Tab / secure browser returns by the existing
  verified app deep link. Mobile also stores only the opaque Worker capability.
- The Worker now exposes origin-bound, rate-limited, no-store Gmail
  list/message/revoke routes. It checks capability type, refreshes credentials
  server-side, and never returns or logs Google bearer/refresh tokens.
- Gmail records and events remain scoped to the initiating Yayra browsing
  profile/window. A renderer-provided profile id cannot cross that trusted
  binding.

### Safe email rendering

- Gmail IDs, labels, dates, headers, snippets, pagination tokens, queries, and
  response sizes are validated and bounded.
- Message HTML is never mounted in the renderer. Plain text uses `textContent`;
  HTML-only fallback is reduced to bounded text before crossing IPC/the Worker.
- Access denial, cancellation, missing scope, expiry, malformed responses, and
  unavailable Worker configuration produce explicit retry/reconnect states.

## Google Cloud / Cloudflare deployment requirements

- Enable the Gmail API in the Google Cloud project.
- Add `gmail.readonly` to the OAuth consent configuration and keep test users
  configured while the app is in Testing mode.
- Gmail scopes can require Google OAuth verification and, depending on Google's
  current policy and deployment, a security assessment before broad production
  use.
- Web/PWA/mobile delegated Gmail records reuse the existing encrypted
  `GOOGLE_DRIVE_SESSIONS` KV and `GOOGLE_DRIVE_SESSION_SECRET` deployment
  bindings for compatibility, with separate `gmail-session:` and
  `drive-session:` keys and distinct authorization schemes.
- No Chrome cookie import, decryption, remote-debugging extraction, or fake
  Google website session was added.

See `docs/GOOGLE_SIGNIN.md` and `docs/CLOUDFLARE.md` for the complete setup,
threat model, routes, and manual verification matrix.

## Honest limitations

- OAuth identity and Google website cookies are different security domains.
  A Google Search/YouTube page can still render Google's own cookie-dependent
  “Sign in” control; Yayra now shows the exact verified app account in a
  separate persistent strip rather than falsely claiming Chrome's cookies were
  imported.
- Gmail inside Yayra is read-only and plain-text-focused in this release.
- Live provider consent was not possible in headless CI. A release operator
  must manually verify desktop loopback, Web callback, Android/iOS deep link,
  Gmail API enablement, consent-screen verification, restart persistence, and
  cancellation on real configured clients.
- Physical `.deb` construction remains blocked only by this sandbox's Electron
  runtime download restriction; static packaging layout and hooks pass.
