# Yayra v1.0.85 — Real Google website sign-in

This release targets one thing: **a genuinely signed-in Google website**, not a
fake avatar and not an OAuth token pretending to be a browser session.

## The problem, stated precisely

Google's own websites (Gmail, Drive, `myaccount.google.com`) authenticate with
**Google website cookies**. Yayra's existing "Sign in with Google" is an OAuth
PKCE app identity: it produces an encrypted API token and a verified profile,
but no Google website cookie. That is why a Google Search tab in Yayra still
showed the blue **Sign in** button even when the Yayra account was connected.

Those cookies cannot simply be copied. Chrome encrypts them with OS-level keys,
and since 2026 Google's **Device Bound Session Credentials (DBSC)** bind Google
account sessions to a TPM / Secure Enclave key that never leaves the device
(Chrome 146+ on Windows; macOS rolling out). A copied cookie is cryptographically
useless on another user agent. Google also blocks sign-in from browsers that are
"embedded in a different application" or "controlled through software
automation" — an explicit list in its *Sign in with a supported browser* help
page — and its OAuth 2.0 policy forbids authorization requests in an embedded
user-agent under developer control.

## What shipped

### 1. Dedicated real Chrome profile (the guaranteed path)

`electron/googleChromeProfile.cjs` launches a **real Chrome / Edge / Chromium
process** with `--user-data-dir=<Yayra userData>/google-chrome-profiles/<profile>`.
That is a separate, Yayra-owned browser profile — the user's personal Chrome is
never touched, and **no cookies are read, decrypted, copied or imported**.

- One profile per Yayra browsing profile, so window/account isolation is preserved.
  A manifest binds each directory to its owning profile id; a mismatch is refused.
- Google's real website cookies (including DBSC-bound sessions) live in that
  Chrome profile and survive Yayra restarts.
- Only exact HTTPS Google-owned destinations may be launched. Lookalike hosts,
  `http:`, credentials, non-HTTPS schemes and oversized URLs are rejected.
- Fixed, minimal launch arguments. No `--remote-debugging-port`,
  `--enable-automation`, `--headless`, custom user agent, or extension loading.
  `unsafeChromeFlag()` rejects those and the whole launch fails closed.
- Discovery is an allowlist of per-OS install paths, with an optional absolute
  `YAYRA_CHROME_BINARY` override. If none is found, Yayra reports
  `chrome_binary_not_found` and falls back to the OS external browser rather
  than faking success.

**One services-consent sign-in, two results.** `electron/authBridge.cjs` now
uses the dedicated Chrome as the RFC 8252 external user-agent for the Google
services consent. The one-shot `127.0.0.1` loopback callback still returns only
the authorization code to Yayra's main process, so the verified Google
services identity, PKCE, `state`, and encrypted token store are unchanged.
Simultaneously, Google creates genuine website cookies in the dedicated Chrome
profile. Yayra's own "Sign in with Google" account flow (`handleSignIn`) is
**untouched**. Opening `myaccount.google.com` directly can establish a Google
website session but cannot report the selected email back to Yayra; use
**Connect & open Google Account** / **Continue with Google** when you want both
the real website session and the exact verified email reflected in Yayra.

### 2. Six best-effort standalone-browser parity fixes

`electron/googleAuthParity.cjs`, `electron/googleAuthUserAgentMetadata.cjs`, and
wiring in `electron/webviewBridge.cjs` / `electron/mediaCompatibility.cjs` /
`electron/autofillPreload.cjs`. All are gated behind a per-profile Security
Center switch, **off by default**.

1. **Honest client hints.** `Sec-CH-UA`, `-Mobile`, `-Platform`,
   `-Full-Version-List` are normalized on Google auth traffic from the real
   Chromium version, plus a best-effort CDP
   `Emulation.setUserAgentOverride` for `navigator.userAgentData`. Brands are
   `Chromium` + a GREASE brand — **never** a spoofed "Google Chrome" identity.
2. **Zero page-script injection on `accounts.google.com`,
   `consent.google.com` and `myaccount.google.com`.** The whole autofill preload
   is gated at document start; text-selection shims, media shims, pointer CSS,
   the WebAuthn watchdog, the Google Search thinking watchdog and the Yayra
   connected-account marker are all skipped there.
3. **No request/header rewriting on auth traffic.** `HTTPS-First`, tracker
   blocking, DNT/GPC injection, topic/attribution stripping, third-party cookie
   removal, `Cache-Control`/`Pragma` overrides and Cloudinary rewrites are all
   bypassed on auth surfaces. `Privacy Shield` remains fully active everywhere else.
4. **No injected WebAuthn shim.** Yayra's virtual passkey provider and
   account chooser are detached/bypassed on auth surfaces. Electron's
   app-mediated discoverable-passkey chooser cannot be made into Chrome's
   trusted native browser UI, so a Google passkey-account selection triggers a
   handoff to the dedicated real Chrome profile. No automation flags are set.
5. **Origin/TLS indicator.** The main process emits a `google-auth-surface`
   event containing **only the HTTPS origin**, rendered alongside Yayra's native
   lock state in browser chrome. Page content cannot paint or influence it; the
   lock reflects Chromium's HTTPS navigation state and is not a Google account
   verification claim.
6. **Automatic fallback.** `/signin/rejected` and `disallowed_useragent` are
   detected in the trusted main process. Yayra opens the same destination in the
   dedicated Chrome profile and tells the user honestly what happened, instead
   of looping the OAuth flow or leaving a dead page.

Third-party OAuth authorization requests always remain in the external browser.
First-party Google sign-in may be attempted inside Yayra only when parity is on;
`isThirdPartyGoogleOAuthUrl()` is a hard guard.

### 3. UI

- **Security Center → Google sign-in**: real Chrome profile status, "Connect &
  open Google Account" (returns the exact verified email and creates the real
  Chrome session), a separate direct website-only open action, the "Open Google
  products in Chrome" toggle, and the "Standalone-browser parity" toggle. Both
  settings are normalized, profile-scoped and persisted.
- **`yayra://google-services`**: a clearly separated "Real Google website
  sign-in (dedicated Chrome)" panel, a "Chrome" button on each service tile when
  a browser is installed, and a link to the settings page.
- **Omnibox**: the main-process-reported Google HTTPS origin alongside the
  native HTTPS lock state on auth surfaces.
- **Truthful Google account strip**: displays the verified Yayra email on Google
  product pages without replacing Google's Sign in button/avatar/account menu.
  It never claims the Yayra WebContentsView has Google website cookies; those
  cookies belong to the dedicated Chrome profile.

### 4. What did NOT change

Yayra account sign-in, Gmail/Drive API mailbox, the Worker and Capacitor OAuth
adapters, all v1.0.84 Privacy Shield behavior off auth surfaces, document
viewers, session recovery, tab groups, and the "Install as app" logo rule.
No sync system was added — Google website sessions are owned by the local
Chrome profile, not relayed between devices.

## Honest limitations

- **Google does not publish a browser allowlist or certification**, and its
  embedded/automation detection is opaque and changes over time. The six parity
  fixes are the best legitimate attempt to satisfy the signals Google documents;
  they **cannot guarantee** that Google accepts an in-Yayra tab. The dedicated
  Chrome profile is the guaranteed path and is always available as a fallback.
- **Desktop only for the dedicated profile.** Web/PWA/mobile cannot launch a
  separate real Chrome process; they keep the existing OS external browser and
  API-backed Google services. The UI reports this instead of faking it.
- **Google pages open in a Chrome window, not a Yayra tab** when using the
  guaranteed path. Window reparenting (Windows/X11) is fragile, breaks on Chrome
  updates and does not work on Wayland, so it was not shipped.
- **A packaged Electron build was not manually exercised against a live Google
  sign-in in this sandbox** (no Chrome runtime / no display). Automated tests
  cover the pure policy, launch safety, isolation and integration wiring.
  A real packaged login on the user's machine is the definitive check.
- **Google scopes.** `gmail.readonly`, `drive.readonly`, Photos and other
  restricted scopes still require Google's verification, a privacy policy and
  any security assessment Google requires for production use.
- Physical Linux `.deb` packaging remains blocked in this sandbox because
  electron-builder cannot download the Electron runtime; this is unrelated to
  the Google work.
