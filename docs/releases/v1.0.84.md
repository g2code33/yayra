# Yayra v1.0.84 — Security Center and Google services sign-in reflection

This release adds a production Security Center matching the supplied Chrome
Privacy & Security screenshots, enforces its controls in the trusted desktop
process, and replaces the previous “Yayra app account only” continuation with
an explicit **Google services connection** that reflects the exact account
chosen in the external browser across Google pages and services inside Yayra.

Application version: **1.0.84**

Android/iOS build code: **1000084**

## 1. Security Center

`yayra://settings` → **Privacy & Security** now provides every destination
shown in the screenshots, with working navigation, toggles, selectors, buttons,
time ranges, lists, and confirmations:

- Safety Check overview with live policy status, blocked-request counters,
  Maximum protection, and shortcut cards.
- Six-step Privacy Guide: welcome, search/browsing quality, threat protection,
  third-party cookies, privacy signals, and review complete. Back, Next, Done,
  radio choices, and every step-level control are functional.
- Delete browsing data with Last 15 min / hour / 24 hours / 7 days / All time
  ranges and separate history, cookie/site-data, cached-files, and autofill
  selections. Desktop clearing is real Chromium session clearing; time-limited
  deletion does not silently over-delete IndexedDB.
- Third-party cookies page with block/allow policy, trusted-site exceptions,
  site-data inspection, DNT and Global Privacy Control.
- Site settings with recent activity, all permission categories, JavaScript,
  images, pop-ups, embedded content, additional permissions, and automatic
  permission cleanup.
- “See all site data and permissions” with real cookie counts from this
  profile's Chromium sessions, search, refresh, per-site delete, and delete
  displayed data.
- Security with Enhanced/Standard/Off threat protection, HTTPS-First, secure
  DNS provider selection, local weak/reused password checkup, JavaScript
  optimization/security, security-key vault access, certificate guidance, and
  Google Advanced Protection information.
- Ad privacy with Ad topics, Site-suggested ads, Ad measurement, DNT, GPC, and
  blocked-site management.
- Permissions with Ask/Allow/Block defaults for location, camera, microphone,
  notifications, clipboard, MIDI, USB, serial, Bluetooth, HID, pointer lock,
  and idle detection, plus saved per-site decisions.

Every setting is normalized, persisted immediately in profile-scoped storage,
and synchronized to the desktop native engine. Malformed policy values fail
closed. Non-desktop builds truthfully report which native operations are
unavailable instead of showing fake success.

### Main-process enforcement

`electron/privacyShield.cjs` and `electron/webviewBridge.cjs` now share one
composed `WebRequest` policy per Electron `Session`:

- HTTPS upgrades before request, with local-host exceptions.
- On-device enhanced threat hardening: malformed destinations,
  credential-in-URL traps, impossible hostnames, suspicious IDN/login patterns,
  oversized URLs, and disabled speculative preload requests.
- Local tracker/telemetry host blocking and user-defined blocked sites.
- Cross-site `Cookie` and `Set-Cookie` stripping with sanitized host exceptions.
- `DNT: 1`, `Sec-GPC: 1`, and removal of ad-topic, ad-auction, and
  attribution-reporting headers when those APIs are off.
- Audited secure-DNS providers only; renderer code cannot supply a resolver URL.
- JavaScript, image, and popup enforcement.
- Native permission prompts with profile-scoped “Ask / Always allow / Block”
  decisions and automatic runtime cleanup.
- Real site-data inventory and per-site deletion on desktop.
- Local password checkup that never uploads vault entries.

See `docs/SECURITY_CENTER.md` for the complete control and threat model.

## 2. Google services connection and visible sign-in reflection

The earlier connection verified a Yayra identity but did not make Google
services account-aware enough for the user's request. v1.0.84 adds a separate
broader Google consent and an in-Yayra Google services session:

- **Continue with Google** now starts the Google services connection from the
  account menu, Settings → Account, Google account entry, product sign-in
  redirects, and `yayra://google-services`.
- The system browser remains the OAuth external user-agent. Returning through
  the verified PKCE callback/deep link persists the exact selected email per
  Yayra profile and across restart.
- A new `yayra://google-services` hub shows the exact connected account, Gmail
  in Yayra, disconnect/switch actions, and more than 30 Google product tiles
  covering Google Account, Gmail, Drive, Docs, Sheets, Slides, Calendar,
  Contacts, Meet, Chat, Photos, YouTube, Maps, Translate, Gemini, Classroom,
  Tasks, Keep, Ads, Analytics, Cloud, and more. Every tile opens inside Yayra.
- Google product pages in Yayra receive a connected-account strip showing the
  exact email. On desktop, a native-page reflection script replaces Google's
  visible leaf “Sign in” label with that verified email and a clear
  “Yayra connected” marker. The script is branded as Yayra, carries no Google
  token, and never creates a fake Google avatar menu.
- If a Google product redirects back to `ServiceLogin`, Yayra returns to the
  services hub with the connected account instead of starting a second OAuth
  loop or pretending Chrome cookies were imported.
- Service destinations carry the selected email as an `authuser` hint while the
  original initiating-destination path/query/fragment behavior from v1.0.83 is
  preserved for OAuth continuation tests.
- Gmail continues to open the read-only API-backed in-Yayra mailbox. Drive API
  download fallback, profile isolation, and all v1.0.82/v1.0.83 recovery
  behavior remain intact.

### API-backed previews

An allow-listed catalog (`src/services/googleServiceCatalog.js`) supplies exact
Google product destinations and read-only API URLs. Desktop and the Worker call
only those URLs with server-held bearer credentials and return normalized
display fields:

- Gmail message counts, Drive/Docs/Sheets/Slides recent files, Calendar events,
  Contacts, Tasks, Classroom courses, Photos items, and YouTube channels.
- Desktop uses the encrypted per-profile main-process auth store.
- Web/PWA and mobile use a new random `YayraServices` capability. The Worker
  stores AES-GCM-encrypted, origin-bound credentials under
  `google-services-session:` keys and exposes `/api/google/services` plus
  `/api/google/services/session/revoke`.
- Responses are bounded, unsafe upstream URLs are discarded, and no Google
  access/refresh token reaches renderer JavaScript, callback URLs, Worker
  responses, or logs.

The explicit read-only scopes are Gmail, Drive, Calendar, YouTube, Contacts,
Photos Library, Tasks, and Classroom courses, in addition to
`openid email profile`. Production deployments may need Google API enablement,
OAuth verification, test users, privacy-policy review, and a security
assessment. See `docs/GOOGLE_SIGNIN.md` and `docs/CLOUDFLARE.md`.

## 3. Cross-platform implementation

- **Desktop:** encrypted scoped auth store, IPC-only Google API calls, native
  Chromium privacy policy/permission prompts, connected-account reflection in
  `WebContentsView`, secure DNS resolver configuration, real site-data
  inventory, and bounded browsing-data deletion.
- **Web/PWA:** full-page external OAuth callback, opaque origin-bound
  `YayraServices` capability, Worker-held encrypted credentials, connected
  Google services hub and exact-account strip, local privacy settings with
  honest native-operation fallbacks.
- **Android/iOS:** Custom Tab / SFSafariViewController consent and verified app
  deep link, same opaque Worker capability, Google services hub, Gmail/Drive
  paths, and profile-scoped privacy preferences.
- **Cloudflare Worker:** new `google-services` OAuth capability, enumerated
  granted scopes, separate encrypted KV prefix, allow-listed service API
  proxy, bounded normalized responses, origin checks, rate limiting,
  no-store responses, refresh, and revoke.

## 5. Honest limitations

- Yayra still cannot copy Google SID cookies from Chrome into its isolated
  Electron/Android/PWA website session. The account reflection is a truthful
  Yayra-owned indicator plus OAuth/API-backed surfaces; it does not claim that
  Google's own cookie-dependent web UI was authenticated by Yayra.
- Google web products that require a live Google website cookie may show their
  own account controls. Yayra's connected strip and services hub remain visible,
  and supported data is provided through scoped APIs.
- The Google services hub currently offers read-only previews and product
  navigation; it is not a full replacement for every Google web editor. Gmail
  remains read-only. Google Docs/Sheets/Slides edits and Gmail compose/send are
  not implemented through this API layer.
- Some Google scopes are restricted. If Google does not grant one, the
  corresponding preview returns `service_scope_required`; other granted
  services and the exact connected account still work.
- Live provider consent, real device deep links, and packaged-Electron Google
  page reflection require a configured Google Cloud project and manual QA.
- Physical Linux `.deb` creation remains blocked only by the sandbox's
  Electron runtime download restriction; static packaging layout, hooks, and
  all nonphysical gates pass.

## 6. Deployment checklist

1. Bump/deploy the Worker with the existing `GOOGLE_DRIVE_SESSIONS` KV and
   `GOOGLE_DRIVE_SESSION_SECRET` bindings and the configured Google client IDs.
2. Enable the Google APIs used by the deployment and configure all enumerated
   read-only scopes on the consent screen.
3. Add test users and complete Google verification/security assessment before
   broad production use.
4. Verify desktop loopback, Web callback, Android/iOS deep link, service
   preview, Gmail continuation, restart persistence, logout/revoke, and
   profile/window isolation on real configured clients.
5. Verify Enhanced protection, cookie blocking, Secure DNS, Safety Check, and
   site-data deletion on a packaged desktop build.
