# Yayra v1.0.48 — Website passkey reliability

## Highlights

- Recognizes standards-based website WebAuthn registration and authentication at document start, including requests made before `dom-ready`.
- Keeps Chromium's real `navigator.credentials.create()` / `get()` ceremony active; Yayra does not replace or mock the site's authenticator request.
- Shows an immediate passkey status indicator in browser chrome and concise in-page guidance if a non-conditional request remains pending.
- Adds native discoverable-account selection and guarantees Electron's selection callback completes exactly once on choose, cancel, close, or error.
- Adds a one-click system-browser fallback for phone, synced, or browser-owned hybrid passkey flows Electron cannot present itself.
- Enables macOS Touch ID website credentials only when the running signed app exposes an exact dedicated WebAuthn keychain access group. Missing entitlements fail closed and are reported honestly.

## Privacy and security

Yayra chrome receives only bounded lifecycle metadata: request ID, create/get action, relying-party ID, mediation/attachment type, success, and error name. Challenges, user handles, account identities, credential IDs, attestation, authenticator data, and signatures remain inside the site/Chromium/authenticator ceremony. The isolated preload and Electron main process both validate the page host and relying-party relationship and enforce lifecycle/rate limits.

Yayra's existing vault-unlock passkey remains a separate, app-owned mechanism. It is never advertised or supplied as a website credential.

## Platform notes

- **Windows:** Windows Hello and Chromium-supported roaming security keys remain the primary in-app paths.
- **macOS:** Touch ID requires a Secure Enclave and matching signed `keychain-access-groups` entitlement; roaming keys remain available subject to Electron's authenticator UI support.
- **Linux:** Chromium-supported roaming keys can complete in-app. Phone/synced passkeys and security-key flows requiring UI Electron does not provide should use the system-browser fallback.
- Passive conditional mediation remains silent until user interaction, avoiding false “stuck request” prompts.
