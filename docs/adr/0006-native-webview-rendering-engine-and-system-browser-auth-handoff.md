# ADR 0006: Native WebContentsView Rendering and External Provider Authentication

## Status
Accepted

## Context
`BrowserShell.js` (the shared floating-browser UI used by every platform target) rendered every visited website inside a plain HTML `<iframe>`. This works for sites that allow being embedded, but a large share of real-world sites - Google, GitHub, Facebook, Microsoft, Amazon, and others - send `X-Frame-Options` / CSP `frame-ancestors` response headers that **forbid any iframe from embedding them at all**. That restriction is enforced by the target site and by the browser engine itself; no amount of configuration on Yayra's own Content-Security-Policy can override a restriction the remote site enforces against being framed. Users navigating to these sites saw either a blank frame or the browser's own inline "refused to connect" error rendered inside the tab.

A second, related but distinct problem: Google documents that OAuth authorization requests are not allowed in embedded user agents ([Google's policy](https://developers.google.com/identity/protocols/oauth2/policies#embedded-webviews)), and its interactive Account sign-in can reject app-controlled surfaces with “This browser or app may not be secure.” A separate Electron `BrowserWindow` remains app-controlled and is not RFC 8252's external user-agent. Ordinary account/product browsing and interactive authentication must therefore be routed separately. Yayra follows provider policy and does not bypass it through cookie copying, user-agent spoofing, or bearer tokens in custom-scheme URLs. Apple/Microsoft retain their existing handoff behavior; this ADR does not claim Google's policy applies identically to those providers.

This repository already has an ADR (0001) describing a long-term target architecture of fully native, per-platform browser engines (`browser-android` via `android.webkit.WebView`, `browser-windows` via WebView2, `browser-linux` via WebKitGTK). Those packages (`packages/browser-windows/src/WindowsWebView2Engine.js`, `packages/browser-linux/src/LinuxWebKitEngine.js`, plus native `.c`/`.cpp` companions) exist today purely as **contract-level simulations exercised by their own unit tests** - they are never imported by `electron/main.cjs`, `electron/preload.cjs`, or `BrowserShell.js`, and therefore have no bearing on what the shipped desktop app actually renders. The desktop app that is actually built and distributed runs on **Electron** (`electron/main.cjs`), hosting `BrowserShell.js` inside Electron's own Chromium renderer. Any real fix had to target that actual, shipping code path rather than the aspirational native-engine packages.

## Decision
**Electron desktop (Windows, Linux):** Real website content is now rendered through Electron's `WebContentsView` (the current, non-deprecated replacement for `BrowserView`; see `electron/webviewBridge.cjs`), attached as a sibling OS surface directly to the application window's `contentView`, positioned over an invisible HTML placeholder element tracked with a `ResizeObserver`. A `WebContentsView` is a first-class sibling surface, not a nested browsing context, so `X-Frame-Options` / `frame-ancestors` never apply to it. The renderer (`BrowserShell.js`) detects this capability via `window.yayra.webview` (exposed by `electron/preload.cjs`) and only falls back to the legacy `<iframe>` renderer when that bridge is absent.

**Identity-provider authentication (all platforms):** Google routing is endpoint-aware, not a blanket Google-host match. On the exact `accounts.google.com` host, recognized routes include third-party OAuth (`/o/oauth2/...`, `/oauth2/...`, `/signin/oauth/...`, `/gsi/select/...`) and first-party Account sign-in (`/signin/v2/...`, `/v3/signin/...`, `/ServiceLogin`, `/InteractiveLogin`, `/AccountChooser`, `/AddSession`). Account root/management and `myaccount.google.com` are also recognized as first-party account intents; logout, Search, Gmail content, and other product routes are not broad-matched.

On Electron, first-party account intents and Google-product redirects into ServiceLogin are canceled before entering `WebContentsView` and request Yayra's own system-browser Authorization Code + PKCE flow. Its random state and one-shot `127.0.0.1` loopback callback return a sanitized profile, focus Yayra, and update the account card/avatar. Captured first-party provider URLs never cross Electron renderer IPC or Android native-to-JavaScript events. Third-party OAuth retains its original client/callback and opens unchanged with `shell.openExternal`. On Android/iOS, the same distinction uses Capacitor Browser plus an exact custom-scheme code/state callback for Yayra identity; token-bearing callbacks are rejected. Web/PWA identity uses full-page redirect, exact same-origin callback, and Worker-side exchange. Apple/Microsoft retain host-based system-browser behavior.

App identity and Google website sessions remain distinct. The source product URL/history is preserved and the connected card can continue only to a sanitized, credential-free Google product origin in the browser that owns its cookies. An arbitrary third-party website OAuth flow may finish in the external browser because Yayra never imports that browser's cookies.

**Known frame-hostile sites (non-auth, e.g. general google.com/github.com browsing) on non-Electron platforms** continue to show an explicit in-app "this site can't be embedded" card with an open action, now routed through the same Capacitor-aware `openExternally()` helper instead of a raw `window.open` call, so the behavior is consistent and testable across platforms.

**Failed website lifecycle (all engines):** A main-frame failure creates tab-scoped recovery state while preserving the requested HTTP(S) URL. Yayra hides the failed native/iframe layer and renders its own browser-style troubleshooting page; it never navigates the tab to an internal error URL. Only the active failed tab retries, using capped backoff and a no-overlap watchdog. An `online` event forces that tab's immediate retry but never refreshes a healthy or background page. Electron exposes a separate retained-URL retry IPC because `webContents.reload()` cannot reliably recover a URL that failed before commit, and sends `load-succeeded` only when `did-finish-load` belongs to a generation without `did-fail-load` (Chromium's own error document is not success). Android likewise reloads the renderer-retained URL, reports main-frame `onReceivedError`, publishes a redirect's final URL, and only then emits positive completion. Navigation, URL change, tab close, or shell teardown cancels the retry generation.

This is an incremental fix to the actually-shipping Electron/Capacitor/web code paths, not a rewrite of the ADR 0001 target architecture; it does not touch or depend on the `browser-windows`/`browser-linux` contract packages, which remain future-facing and unaffected.

## Consequences

### Positive
* Real-world sites that previously failed to load at all (Google, GitHub, etc.) now load correctly on Electron desktop, with no change to CSP relaxation that would weaken the app's own security posture.
* The floating browser's UI/UX (tab strip, resize/minimize/maximize/close, omnibox, history, bookmarks) is completely unchanged - only the content-rendering internals were touched.
* Google auth uses the OS external user-agent required by provider policy. First-party Account entry now returns a verified profile to Yayra instead of reopening a raw login that can never update the app; third-party OAuth remains untouched. The source tab/history stays unchanged, rejection URLs enter the connection flow, no captured authorization URL is echoed over IPC, no browser cookie is imported, and ordinary product routes remain normally routable.
* The endpoint classification, navigation/popup handoff, tab/history preservation, and OAuth callback/PKCE guards are covered by deterministic tests (`tests/electron-webview-bridge.test.mjs`, `tests/browser-shell-native-engine.test.mjs`, `tests/browser-shell-capacitor-handoff.test.mjs`, `tests/android-inapp-google.test.mjs`, and the Google auth/Worker suites) against mocked Electron/Capacitor APIs.
* Failed pages never depend on the remote renderer to explain themselves: the address remains intact, recovery UI stays visible through retries, and connectivity restoration targets only the failed active tab. `tests/network-recovery.test.mjs` pins timer, URL, background-tab, native-success, Android-event, and web-frame behavior.

### Negative / Known limitations
* External browser cookies are intentionally not copied into Yayra. A third-party website's OAuth callback can therefore remain in the external browser rather than signing in the untouched embedded website tab. App-level Yayra identity has its own verified callback and returns correctly on every platform.
* No real Google consent/sign-in was manually tested for this change. Deterministic mocks cover routing, URL/history preservation, state, PKCE and callback rejection; a human with a configured OAuth client and real desktop/mobile device must still run the manual QA checklist.
* Electron itself cannot be launched inside this project's CI/dev sandbox, so `electron/webviewBridge.cjs`, the OAuth loopback, IPC, and shell handoff are verified against mocks and local sockets rather than a live Google consent page. Manual verification on a real desktop build is still required.
* `goBack()` / `goForward()` on the native engine re-drive navigation by calling `ensure()` with the previously tracked URL rather than invoking Chromium's native `webContents.goBack()`/`goForward()` history traversal; this is functionally correct for URL display but does not share a single history-entry list with Electron's own back-forward cache. A future iteration could thread real back/forward state through if this proves insufficient.
* Android already has a per-tab native WebView manager for frame-hostile pages (`packages/floating-android/.../YayraTabWebviewManager.kt`); this change adds auth-navigation and popup interception there, but does not move every embeddable site from the existing iframe path into that engine. iOS continues to use the existing WebView/iframe path plus Capacitor Browser for sign-in. The Android source was not compiled or run on a device in this sandbox, and iOS requires Xcode for native build verification.
* The provider host list and exact Google OAuth/interactive-sign-in predicates are intentionally duplicated across `electron/webviewBridge.cjs` (Electron main process), `BrowserShell.js` (renderer/web/Capacitor bundle), and Android's `YayraTabWebviewManager.kt`. These runtime boundaries use different module/language systems; each copy points to the others, and parity is covered by tests.
